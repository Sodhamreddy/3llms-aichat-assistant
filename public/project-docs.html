Project Overview & Purpose

🎯 What is Kleza Excelliq AI?

Kleza Excelliq AI is a productivity and research tool built by Kleza Solutions Pvt Ltd. It solves a common problem faced by AI power-users: different language models give meaningfully different answers to the same question, and manually switching between ChatGPT, Claude, and Gemini is slow and tedious.


Excelliq lets you type a prompt once and instantly see all three responses in a clean, side-by-side comparison view — then Claude synthesizes the best elements of all three into a single high-quality final answer. The platform also tracks your token usage and estimated cost per run.

⚡ Speed

All three models are queried in parallel — you get three answers in roughly the same time it takes to get one.

🧠 Synthesis

Claude reads all three stage-1 responses and synthesizes the most complete, accurate answer from the combined output.

📊 Tracking

Every run logs token counts, estimated costs, response times, and the full conversation — all stored locally in the browser.

🔀 Two Operating Modes

API Mode (default)

Prompts are sent through an n8n automation workflow hosted at n8n.kleza.io. n8n calls each model's API endpoint in parallel and returns structured JSON with each model's response plus a Claude synthesis. No local server required.

Browser Mode

A local Playwright server (Node.js + Express) drives a real Chromium browser in the background, navigating to the actual chat interfaces of ChatGPT, Claude.ai, and Gemini.com. This requires a one-time login but uses no API keys and has no per-token costs.

📋 Step-by-Step Data Flow

1

First Visit — Landing & Onboarding

User lands on the marketing page (LandingPage.jsx). On "Get Started", they are taken to a 3-step onboarding wizard where they enter their name, email, choose which models to enable, optionally enter API keys, and select API or Browser mode. Results are saved to localStorage under the key ph_user.

2

Prompt Entry

User types a prompt in the auto-growing textarea inside PromptControl.jsx. They can toggle mode (Battle vs Invisible), select which models to include, switch between API and Browser mode, or enable Deep Research before submitting. Enter submits, Shift+Enter adds a newline.

3

Request Dispatch

On submit, handleRun() saves the prompt to submittedPrompt state (so the input clears but the question bubble remains visible), then calls either handleRunN8N() or handleRunPlaywright() depending on the selected mode. An AbortController is created so the user can stop mid-run.

4

API Mode — n8n Processing

A POST is sent to the n8n webhook with the prompt, selected models, session ID, and any API keys from ph_user. n8n calls ChatGPT, Gemini, and Claude in parallel. The response JSON contains raw.openai, raw.gemini, raw.claude (stage-1), and raw.output (Claude's synthesis). The frontend parses these fields.

5

Browser Mode — Playwright Streaming

A POST is sent to localhost:3001/run-prompt. The Express server calls scraper.js which uses Playwright to open (or reuse) hidden Chrome tabs for all three services, pastes the prompt, waits for the response, and streams back partial results as Server-Sent Events (SSE). The frontend reads the SSE stream and updates each model card in real time as text arrives.

6

Response Rendering

Three cards (ChatGPT | Gemini | Claude) appear side by side during loading with animated dots. As content arrives, cards fill with markdown-rendered text. Once all models complete, Claude's final synthesis appears as a distinctive bubble below the three cards with its own copy button and elapsed time.

7

History Persistence

After each run, App.jsx calls handleRunComplete() which adds an entry to the history state array (max 100 items) with the full prompt, all three responses, token counts, cost estimates, and elapsed time. The array is synced to localStorage (ph_history) via a useEffect.

8

Follow-Up Conversations

After a completed run (or when viewing history), the user can type a follow-up question. The follow-up is sent to the n8n webhook with the original prompt and previous answer as context. Claude responds and the follow-up pair is appended to the conversation in both the UI and localStorage.

Edit display name and email. View, add, or update API keys for each model (with show/hide masking). Toggle models on/off. Reset all usage statistics. Links to the Browser Mode login helper.

Reference cards for GPT-4.1 Mini, Claude Haiku 4.5, and Gemini 1.5 Flash. Shows context window, per-token pricing, key strengths, and an enable/disable toggle per model.

📈 AnalyticsPage.jsx

Weekly bar chart of runs per day, token usage by model (bar), and cost breakdown pie chart. All data sourced live from localStorage history — no external analytics service.

⏰ AutomationsPage.jsx

Create and manage scheduled prompt jobs with frequency templates (hourly, daily, weekly). Jobs can be enabled/disabled and deleted. UI only — scheduling logic connects to n8n.

🔌 IntegrationsPage.jsx

Configure the n8n webhook URL, manage API keys for integrations, and set output delivery channels: Slack (webhook URL), Email (SMTP), WhatsApp (Twilio), Google Sheets (spreadsheet ID). The page shows connection status for each channel.

Backend — Playwright Server

ℹ️ The Playwright server is only required for Browser Mode. In API Mode, all traffic goes directly from the browser to the n8n webhook — no local server is involved.

🖥️ server.js — Express API (port 3001)

A lightweight Node.js/Express server that acts as the bridge between the React frontend and the Playwright browser automation layer.

MethodRoutePurposeResponse
POST
 /run-prompt Send prompt to all 3 LLMs in parallel. Accepts { prompt, selectedModels, deepResearch } Server-Sent Events (SSE) stream — emits partial events and a final complete event
POST
 /follow-up Follow-up question with context. Accepts { question, originalPrompt, previousAnswer } SSE stream — same format as /run-prompt
POST
 /show-chrome Move the hidden Chrome window back onto the screen so the user can log in JSON { ok: true }
POST
 /hide-chrome Move Chrome window off-screen to -32000, -32000 after login JSON { ok: true }

🎭 scraper.js — Playwright Automation Logic

The core automation file. It maintains a single persistent Chromium browser instance (using a saved profile) and controls hidden Chrome tabs for each LLM service.


How browser mode works step by step:

1

Persistent Browser Launch

On startup, Playwright launches Chrome using the browser-profile/ directory as the user data directory. This preserves all cookies and sessions between server restarts. The window is positioned at (-32000, -32000) and minimized — invisible to the user.

2

Parallel Prompt Dispatch

runPromptOnAllLLMs() opens (or reuses) tabs for chat.openai.com, claude.ai, and gemini.google.com. It uses Promise.all() to send the prompt to all three simultaneously.

3

Prompt Injection

Each service's textarea/contenteditable is located with Playwright selectors. The prompt is pasted using page.evaluate() to set the value and dispatch input events — mimicking real typing to avoid bot detection.

4

Response Extraction

Each model's response area is polled until the "stop generating" button disappears (or a timeout is hit). The full response text is then extracted. Claude responses are cleaned by extractClaudeOutput() to remove UI text that leaks into the DOM.

5

SSE Streaming

Partial results are emitted as SSE events as each model finishes. The frontend updates the corresponding model card in real time. Once all three are done, a final complete event with all results and timing is sent.

⚠️ The Playwright server uses an isRunning flag to prevent concurrent prompt executions — only one prompt can run at a time in Browser Mode.

🔐 login.js — First-Time Browser Login

Run once with node login.js. This opens Chrome visibly and navigates to ChatGPT, Claude, and Gemini. The user logs in manually to each service. Session cookies are automatically saved to the browser-profile/ directory and reused on every subsequent server start — no re-login needed.

Security Notes

🔒 API keys are stored in browser localStorage — they are not encrypted. Anyone with access to the user's browser DevTools can read them. This is acceptable for a personal/team internal tool but not for a public deployment. Consider storing keys server-side for production use.
⚠️ The Playwright server has no authentication. It should only ever be run on localhost — never exposed to a public network or the internet.
⚠️ The browser-profile/ directory contains logged-in sessions for ChatGPT, Claude, and Gemini (cookies/tokens). Treat it like a password file — do not commit it to git, share it, or store it insecurely.
✅ API keys are never sent to any Kleza server. In API Mode, only the prompt text and selected models are sent to the n8n webhook. API keys are included in the request body when the n8n workflow is configured to accept them, but never logged or stored externally.
12

Known Limitations

💾 Storage cap — 100 history items

localStorage has a ~5MB size limit per origin. History is capped at 100 entries. Older entries are silently dropped when the limit is reached. For larger history needs, an export feature or IndexedDB migration would be required.

🖥️ Browser Mode requires local server

The Playwright server must be running on the same machine as the browser. It cannot be deployed to a remote host in its current form, as it needs a display and logged-in browser sessions.

🌐 Deep Research — Browser Mode only

Deep Research uses Playwright to leverage each model's built-in web-search feature (ChatGPT Browse, Gemini with Google Search, Claude with web tool). It is not available in API Mode and has a 600-second timeout.

👤 Single-user, single-device

All data (history, usage, API keys, profile) is scoped to the browser's localStorage. Data does not sync across devices or browsers, and there is no multi-user or account system.

📊 Analytics uses estimates

When n8n does not return actual token usage data, the app estimates token counts from character length (chars ÷ 4). Real token counts may differ, especially for non-English content or code-heavy prompts.

🔄 No real-time sync

If the user has multiple tabs open, state changes in one tab (e.g., a completed run) are not reflected in other tabs until the page is refreshed. This is a limitation of localStorage-based state.
